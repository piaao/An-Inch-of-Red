# 预制地图 · 六张图、名册与选择

> **一句话**：程序化生成这条路暂时搁下，改成**手工预制**六张图 —— 一张原始公寓、五张新图（小 2 / 中 2 / 大 1）。尺寸词汇（小 / 中 / 大）不是标签，是**可断言的单调性**；每张图的房间有名字，每种布局有自己的一句话风格。进游戏先选地图与难度。

所有读数来自 `reports/maps.txt` 与 `reports/menus.txt`（都是跑出来的，不是写出来的；
装配命令在各自文件头）。本文件引用到的每个数字都能在那两份里 grep 到。

---

## 一、为什么不是生成器

生成器（`scripts/procgen.mjs` / `procgen.html`）能造出**能走、能玩、布置合理**的户型，
但造不出**有性格**的户型。它产出的房子像它自己，不像一个地方：房间比例趋同、动线趋同、
家具组合趋同。手工预制的成本高在**一次**，收益在**每一局**——一张图可以为了「客厅是枢纽」
把八个房间排成一棵树，也可以为了让「先远后窄」成立而把长廊横过来。生成器要抽到那样的形状
得靠运气，而一张手搓的图是靠意图。

**这不是「生成器不好」，是「生成器的验收标准与『好玩』不是同一件事」。**
生成层的结论与被推翻的东西都留在 `SCENE.md` 与 `reports/procgen.*`，没有删。

## 三、尺寸词汇（小 / 中 / 大）是事实，不是标签

需求原话是「小型地图物品多，房间少；中型平衡；大型地图房间多，大」。这句话在**标签**上
无法检查（谁都能把一张图叫「大」），在**读数**上可以。于是它变成三条断言，写在
`scripts/verify_maps.mjs` 第 6 节：

| 轴 | 小 | 中 | 大 | 断言 |
| --- | --- | --- | --- | --- |
| 房间数 | 2, 3 | 6, 8 | 11 | 小 < 中 < 大 |
| 面积 m² | 48, 63 | 117, 140 | 252 | 小 < 中 < 大 |
| 件/m² | 1.729, 1.381 | 1.179, 1.085 | 0.976 | 小 > 中 > 大 |

三条**同时**成立才算数。任何一条被一次布局改动作反（比如给一人间加两间房），
`verify_maps` 立刻红——而不是等玩家发现「小图怎么这么大」。

**大图为什么不是「更大的小图」**：如果只是把一人间等比放大，件/m² 会保持不变，
于是「房间多、跑得远」这条设计意图既没被满足也无法被检查。大宅的体积来自**房间数**
（11 间）与**中厅**（42.3 m² 横贯全宅），而不是把家具摊薄。

## 四、逐图：风格与它想让你遇到的事

风格写在 `game/maps/index.js` 的 `style` / `blurb` 里，并由 `game/maps/prose.js` 核对——
**散文里出现的每个数字都必须是实测值**（这条规则的由来见 `index.js` 文件头）。

### 原型 · 剖面公寓 `room_scene`（10×8 · 6 间）

两带六室。**这是基准图**：`game/VERDICT.md` 里几乎每一个读数都是在它上面量的，
所以它不改——改它等于让过去的所有测量失去参照物。它由 `scripts/snapshot_arena.mjs`
从 `js/layout.js` 生成，是六张图里**唯一不由 `build_maps.mjs` 重建**的一张（`layout: null`）。

### 小 · 一人间 `studio`（8×6 · 2 间 · 件/m² 最高）

一室到底。**厨房、床、书桌、沙发在同一片地上**，只有一个房间可去，所以没有门框告诉你
走到哪了。它是**最难读**的一张图：全图 48 m²、83 件家具，视线永远被切碎，
找红包靠的是「这件东西后面还没看过」而不是「哪间房还没进」。

### 小 · 藏书房 `den`（9×7 · 3 间）

书墙围合。每一条视线都被书脊挡住，但**家具是薄片**（书架、矮柜），
所以地面被切碎而**不堵**。和一人间同一个尺寸量级（3 间 / 63 m² / 87 件），
玩起来却像迷宫——这是「尺寸相同、性格不同」那一对。

### 中 · 两室一厅 `twobed`（14×10 · 8 间）

中轴对称，南北两带。**动线是一棵树**：客厅是枢纽，每间房都与你已经进过的某间房隔一道门。
近七成地面是空的，**能跑起来**——它是六张里节奏最快的。

### 中 · 茶室小院 `teahouse`（13×9 · 6 间）

东西长廊，中间一条横廊把北侧切成三间。**形状与两室一厅相反**：先是大房间的远视线，
后是小房间的窄拐角；房间更少（6 : 8）但每间更大（最大 21.8 m²），
所以它是「平衡」的另一半，而不是两室一厅的弱化版。

### 大 · 大宅 `manor`（18×14 · 11 间）

中厅为轴。入户门在西南角、主卧在西北角，中间隔着一间横贯全宅的中厅（42.3 m²）。
252 m² 是原始公寓的三倍多，但**家具只多一倍**（246 : 119）：大宅的成本是**跑动**
（一次扫描走不完西半边），不是**找不到**。

## 五、本轮抓到的两条引擎级静默降级

两条都不是新图的 bug，是**引擎原本就会犯、只是以前没有那种平面所以没被触发**的错。
两条都修在引擎里，不修在图里。

### 1. 出生点不在导航格上 ⇒ 整张攀爬图塌掉

`game/core/climb.js` 用 `nav.componentAt(level.spawn.x, level.spawn.z)` 求「出生区域」，
而 `componentAt` 是**格子查询**：出生点落在一个被家具膨胀掉的格子上就返回 `-1`，
于是 `grounded` 对**任何**格子都不成立，`reached` 为空 ⇒ 没有攀爬视点 ⇒
**所有台面锚点被判 `hidden`** ⇒ 锚点池从三十几个塌到个位数。

触发它的是「一人间」：出生点落在一只垃圾桶的膨胀范围里。
**表面症状是「这张图能藏红包的地方特别少」，看起来像关卡设计问题，实际是量具问题。**

这段不再是散文。`reports/maps.txt` 里有一段**出生点探针**，对六张图逐一打印身体半径
（`0.12`）、出生点所在格到底是不是可行走格、到最近实体的间距，以及攀爬图认定的家在哪。
修好之后六张图的 `cell` 一栏都 ≥ 0、间距都 > `0.12`（现在最小的是茶室小院 `0.1669`）；
任何一张图再把出生点放进家具里，那一栏会直接写出 `NO`。

两处修：
* `game/core/climb.js` 用 `regionOf()`——`componentAt` 失败时问 `nav.nodeOf()`（新增导出）
  要「该格不可行走时的最近可行走格」，再取它的连通域；`grounded` 的落点判定同样改走它。
* 数据上把那只垃圾桶挪开：现在在 `(5.78, 5.15)`，离出生点 `0.5166` m
  （探针那一行写的就是它）。

现在由 `verify_maps` 的两条断言守着：`the climb graph is not empty`（`reached.size > 0`）
与 `its anchor pool can host the largest preset`（`pool >= 24`）。变异 M5「清空攀爬图」
证明这两条会红。

### 2. 两间房的图上，第二个守卫是第一个的影子

`buildPatrol` 里唯一的随机抽样是 `rng.shuffle(rooms)`——**房间顺序**。
一人间与藏书房只有 2–3 间房，可选的房间顺序极少，于是两条独立的随机流很容易撞出同一条路线，
第二个守卫就成了影子（不是「难一点」，而是**少一个守卫**）。

修法是**调用方选择性**：`buildPatrol` 增加 `opts.alt`（默认 0），进房后先跳过一个停靠点；
`game/play/boot.js` 只对 `i > 0` 传 `{ alt: i }`——守卫 1 的路线一比特都不动，
因为 `game/VERDICT.md` 量过的那条路线就是它。`verify_maps` 断言
`the second guard does not walk the first one's route`，并**同时**断言
`patrol[0] is bit-for-bit the same with or without patrol[1]`（`verify_packets.mjs`
在上架公寓上做过同一条断言，这里对六张图各做一遍）。

## 六、选择：进游戏先选地图与难度

`play.html` 的开始页现在有两行卡片：**上排地图（6 张），下排难度（4 档）**，最上面一条
实测数字带，然后一颗「开始」。

### 为什么换地图是一次页面重载

`start()` **只建一次**场景图：地板平面、灯光、要下载哪些模型、公寓网格——四件都是平面尺寸
的函数。在活着的场景下换地板，等于把 `start()` 写第二遍，而**第二份 boot 正是整个 arena
工作要消灭的那类 bug**（曾经出现过「生成 16×14 的地板、却在 10×8 的公寓里玩，
而所有量具全绿」）。

所以选择走 URL，页面重载：

| 参数 | 意思 |
| --- | --- |
| `?map=<id>` | 哪张地板。经**名册**解析，不靠拼路径 |
| `?difficulty=<id>` | 预选哪张难度卡 |
| `?seed=<s>` | 钉住的种子，跟着重载一起走 |
| `?markers=0` | 红点开关，也跟着走 |
| `?play=1` | 地板建好就直接开局（重载落地即用，不再问一遍） |

`?play=1` 是**一次性**的：读完就用 `history.replaceState` 摘掉，所以按 F5 会落回菜单
（带着同一张地图与难度），而不是又开一局。

### 名册 id == arena 自报名（本轮修掉的一个真缺陷）

菜单判断「现在站着的是哪张图」靠 `level.meta.id === 名册 id`。而名册把上架公寓
键作 `origin`，`snapshot_arena.mjs` 写进产物的却是 `meta.id: 'room_scene'`——
**两边没人比过**，于是默认落地页六张卡片一张都不高亮，看起来完全正常。

修法：名册改用**地板自己报的名字**（`room_scene`）。没有去改名册里的 71 KB 产物：
`game/arenas/room_scene.json` 是 `game/VERDICT.md` 里所有测量的基准，
为了迁就一个昵称去改它才是本末倒置。

新断言（`verify_maps` 第 1 节）：**名册 id 就是 arena 自报的 id**，对六项逐一核对。
它是**先写、先红、再改数据**的：断言写下去的第一版就红，报的是
`"room_scene" vs meta.id "origin"`；改完名册才绿（`208/208`）。

红的那一次也留了**可复现的证人**：`reports/maps.txt` 里的变异 **M0** 就是把 arena 的
自报名改回去，它至今仍然会红。改之前的那个计数器（初版报的是 `207/208`）没有留在任何
报告里，也不可复现 —— 所以这里不引它，只引能重跑的证人。

### 页面侧另外两处修正

* 数字带上写死的 `/6 房间` 改成 `${s.rooms}/${s.roomsTotal}`。写死的那版对六间房的
  上架公寓是对的，对十一间的大宅是**谎话**，而且**没人能发现**——因为它是个字面量。
  现在由 `verify_menus` 用一个「3 / 11」的摘要反证它必须是算出来的。
* 页面此前**完全无法访问名册**。现在 `play.js` 读的是**产物** `game/maps/manifest.json`
  （不自己从布局模块重算房间数与件数——那会变成同一件事的第二份答案，
  而菜单就获得了与闸不一致的自由）。

## 七、产物从哪来 · 怎么跑

```bash
node scripts/build_maps.mjs        # 五张图 → game/arenas/maps/*.json + game/maps/manifest.json
node scripts/verify_maps.mjs       # 208 条断言（本机可跑，零浏览器、零子进程）
node scripts/verify_menus.mjs      # 44 条断言（真构造 Hud、真点卡片、真按开始）
python scripts/smoke_serve.py      # 启动器：33 个资源 + 六张地板在 HTTP 上取得到
```

| 文件 | 是谁 |
| --- | --- |
| `game/maps/index.js` | **源**：id / 名字 / 类别 / 风格 / 散文。散文里的数字由 `prose.js` 核对 |
| `game/maps/prose.js` | 散文数字校验器：认不出单位的数字也算错 |
| `game/maps/*.js` | 五张图的平面数据（尺寸 / 房间 / 墙 / 门 / 家具），由 `build_maps.mjs` 建 |
| `game/maps/manifest.json` | **产物**：菜单读它，`verify_maps` 拿它与源对账 |
| `game/arenas/maps/*.json` | **产物**：五张 arena 快照（`verify_maps` 逐字节重建比对） |

`build_maps.mjs` 只写 `game/arenas/maps/`、`game/maps/manifest.json` 与
`work/build_maps.log`——**它不碰 `reports/`**，入库证据由 `work/_mkreports.py` 显式装配。

### 验收的两种证据，别混着数

`verify_menus.mjs` 的输出里两段是分开标注的：

* **BEHAVIOURAL** —— 真的 `new Hud()` 打到桩 DOM 上，跑真的 `showStart`，
  **点一张卡片**，再**按「开始」**，把 `onStart` 收到的东西读出来。
  这是「点选的地图真的被交出去」的直接证据。
* **STATIC** —— `play.js` 不能在本进程 import（`three` 是浏览器的 import map，不是 Node 包），
  所以它的接线是**读源码**断言。这比上面弱，因此单独标注，而不是混进同一个总数里装作一样强。

`verify_menus` 还做过**五枚变异**（M6–M10：把分母写死、把插槽删掉、把地图参数丢掉、
不往 URL 写 `?map=`、把选中态的 CSS 顺序反过来），五枚全红、文件全部逐字节还原。
`verify_maps` 另有**六枚**（M0–M5：M0 就是把 arena 的自报名改回去，也就是那个真的上过线的
缺陷）。两张表都在 `reports/` 里。

> **本机限制**：需要 spawn Chrome 的验收（`verify_play` / `verify_world` / `verify_open` /
> `verify_gen_play` 等）在本宿主跑不动（`spawnSync` `EBUSY`）。所以**地图栏的浏览器侧
> 没有被端到端跑过**——能跑的是上面那三把单进程闸；「六张地板在 HTTP 上真的取得到」
> 由 `smoke_serve.py` 真的起一个 `serve.py` 来证。
